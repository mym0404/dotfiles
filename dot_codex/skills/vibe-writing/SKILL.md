# vibe writing

독자가 무엇을 이해하거나 할 수 있어야 하는지 정하고, 그 결과에 필요한 구조·근거·예시·문장을 쓴다. 제목·개요·목차 규칙은 해당 요소가 있는 출력에만 적용한다. 분량과 설명의 깊이는 요청과 독자 수준에 맞춘다.

## 독자와 중심 질문을 정한다

자료와 요청에서 독자, 이미 아는 내용, 해결하려는 질문, 읽은 뒤의 판단이나 행동을 파악한다. 알 수 있는 내용을 다시 묻지 않는다.

한 문서는 중심 질문에 답한다. 같은 주제라도 처음 배우기, 작업 수행, 값 찾기, 원리 이해는 읽는 목적이 다르다. 여러 목적이 섞이면 주된 목적에 맞춰 흐름을 정하고 보조 설명을 배치한다. 독자가 이미 아는 배경은 반복하지 않고, 답을 이해하는 데 필요한 선행 지식만 설명한다.

## 목적에 맞는 흐름을 고른다

| 문서의 목적 | 기본 흐름 | 작성 기준 |
| --- | --- | --- |
| 처음 배우기 | 목표 → 준비 → 간단한 예제 → 단계별 확장 → 결과 확인 | 시작하기는 필수 개념과 전체 흐름을, 튜토리얼은 완성할 결과물을 중심으로 쓴다 |
| 특정 작업 수행 | 목표 → 필요한 조건 → 실행 절차 → 확인 | 배경지식이 있는 독자가 바로 적용할 코드·명령·설정을 제공한다 |
| 오류 해결 | 증상·발생 조건 → 원인 → 해결 → 재확인 | 현상과 원인을 구분하고, 확인한 에러 메시지·로그가 있으면 포함한다. OS·버전·설정에 따른 차이도 설명한다 |
| 값과 동작 참조 | 용도 → 시그니처·입력 → 출력 → 예제·제약 | 항목마다 같은 순서로 쓰고, 처음 사용하는 데 필요한 인증·공통 설정은 앞에 둔다 |
| 원리 이해 | 해결하려는 문제 → 개념·원리 → 선택 이유·대안 → 사용 사례 | 사용 절차 나열보다 동작 원리와 선택에 따른 장단점을 설명한다 |
| 설계·리서치 | 결론 → 조건 → 비교·근거 → 적용·미확인 | 어떤 조건에서 결론을 적용할 수 있는지 드러낸다 |

이 흐름은 고정 목차가 아니다. 필요한 부분만 쓰고, 빈 섹션이나 자료 없는 항목을 채우지 않는다. 답을 좌우하는 필수 정보가 없으면 무엇이 부족한지 묻는다.

학습·작업 문서는 준비부터 완료까지 끊기지 않게 연결한다. 환경과 의존성, 입력할 명령과 변경할 파일, 단계별 예상 결과를 제공한다. 코드 예제는 설명하려는 기능에 집중하며 현재 API와 버전에 맞아야 한다. 실행 가능한 예제는 직접 확인하고, 실행하지 못했다면 검증한 것처럼 쓰지 않는다.

핵심 절차를 방해하는 추가 예제·심화 설명·자주 발생하는 문제는 뒤쪽에 두거나, 매체가 지원하면 접을 수 있는 영역에 둔다. 진행에 필수인 조건과 경고는 해당 단계 앞에 보이게 쓴다.

## 제목과 개요로 답의 범위를 보여준다

제목은 내용을 예상할 수 있는 주제형으로 짧게 쓴다. 독자가 검색할 기술명·작업명·에러 코드를 포함하고, 목록과 상세에는 같은 제목을 쓴다. 같은 수준의 제목은 명사형 또는 동사형 같은 문법 형태를 맞춘다. 순서가 중요한 단계에만 번호를 붙인다.

주장이나 핵심 결론은 제목 아래 개요에 둔다. 독자가 얻는 결과와 본문의 범위를 먼저 쓰고, 필요한 조건이나 배경을 잇는다. 결론을 아직 확인할 수 없다면 확인한 범위와 부족한 근거를 밝힌다. ‘이 문서에서는’으로 주제만 반복하지 않는다.

- 제목: API 요청 재시도 설정
- 불충분한 개요: 이 문서에서는 재시도 설정을 설명한다.
- 개선한 개요: 일시적인 연결 실패가 발생하면 요청을 최대 세 번 다시 보낸다. 재시도할 오류와 중단할 조건, 설정 방법을 설명한다.

제목 끝의 마침표·느낌표와 호기심만 유발하는 질문형 제목을 피한다. 실제 FAQ의 질문과 즉시 이어지는 답은 예외다.

## 정보의 순서와 위치를 예측할 수 있게 한다

각 섹션과 문단은 하나의 주제를 다룬다. 섹션의 첫 문장은 해당 부분의 요지를 전달하고, 뒤의 설명은 그 요지를 뒷받침한다. 기본 개념에서 세부 동작으로, 선행 작업에서 그 결과를 사용하는 작업으로 이어지게 쓴다.

같은 수준의 제목은 같은 종류의 정보를 나타낸다. 제목 수준은 의미에 따라 정하고 시각적 크기 때문에 건너뛰지 않는다. 하위 제목이 계속 깊어지면 서로 다른 질문이나 과도한 세부 정보가 섞였는지 살핀다. 페이지 길이나 제목 깊이만으로 문서를 나누지는 않는다.

서로 독립적으로 찾는 주제는 별도 문서로, 여러 주제를 소개하는 문서는 개요와 링크로 구성할 수 있다. 반대로 앞 단계의 결과가 다음 단계에 필요한 절차나 하나의 결정을 기록한 문서는 함께 둔다. 기존 문서가 있으면 관련 내용을 복제하기보다 필요한 지점으로 연결한다.

같은 종류의 문서에서는 섹션 이름과 순서를 맞춘다. 긴 참조 문서는 기능별 섹션·목차·앵커로 필요한 항목에 바로 접근할 수 있게 한다. 링크 문구에는 연결 대상의 주제나 작업을 드러낸다.

## 개념·조건·예시를 연결한다

독자에게 낯선 핵심 개념은 용도를 이해할 수 있게 설명한다. 용어를 같은 용어로 되풀이하지 않는다. 코드·표·그림 앞에는 이해에 필요한 맥락만 쓰고, 자료 자체로 드러나는 내용을 전후에 반복하지 않는다.

복잡한 구조·데이터 흐름·상태 변화는 그림이나 다이어그램이 관계를 더 명확하게 보여줄 때 사용한다. 같은 속성을 비교할 때는 표를 쓰고, 단순 설명을 표 셀로 잘게 나누지 않는다.

입력값·현재 상태·시간에 따라 동작이 달라지면 조건별 결과를 설명한다. 변수·속성은 의미·타입·형식·단위·기본값·필수 여부·허용 범위 중 사용에 필요한 정보를 제공한다. 참조 문서에는 반환값·오류·제약도 포함하고, 값과 동작은 현재 제품과 대상 버전에 맞춘다.

앞에서 만든 값은 처음 소개할 때 용도를 알리고, 다시 사용할 때 얻은 단계나 위치를 연결한다. 독자가 그 값의 출처를 찾으려고 앞 내용을 다시 뒤지게 하지 않는다.

## 사실·판단·미확인을 구분한다

결론은 확인한 자료·코드·측정 결과로 뒷받침하고, 판단은 근거에서 무엇을 추론했는지 설명한다. 개인의 선호를 객관적 측정으로 표현하지 않는다.

‘빠르다’, ‘많다’, ‘일부’, ‘적절하다’는 확인된 조건·기준으로 구체화하고, 수치에는 적용 범위와 단위를 붙인다. 구체화할 근거가 없으면 수치를 만들거나 가능성을 확정하지 않는다. 무엇을 확인하지 못했고 어떤 결론에 영향을 주는지 밝힌다.

실제 개인정보·인증 키처럼 발견한 민감정보는 문서에 옮기지 않고, 목적에 필요한 대체값을 사용한다.

근거 없는 권위나 중요성을 덧붙이지 않는다. ‘전문가들은’ 대신 실제 출처와 주장을 쓰고, ‘보여준다·상징한다·보장한다’는 자료가 뒷받침할 때만 쓴다. 지식 한계 고지와 한정·면책 문구는 판단에 필요한 만큼만 쓴다.

## 주체와 행동이 드러나는 문장을 쓴다

작업을 안내할 때는 독자가 할 행동을 직접 쓴다. 시스템의 동작을 설명할 때는 실제로 동작하는 구성요소를 주체로 쓴다. 문맥상 명확한 주어를 반복할 필요는 없지만, 행동의 주체·대상·위치·조건을 독자가 추측하게 하지 않는다.

한 문장에는 중심 생각 하나를 담는다. 조건·원인·결과의 관계를 유지하면서 긴 수식과 여러 행동을 나누고, 관련 문장을 접속어 없이 단편적으로 늘어놓지 않는다.

동사에서 파생된 명사와 ‘수행·진행·처리’를 겹치지 말고 실제 행동을 쓴다. ‘~를 통해·~에 있어서·~함으로써’도 실제 수단과 행동으로 간결하게 표현한다. ‘서버를 찌른다’ 같은 비유 대신 요청·응답·저장 등 실제 동작을 쓴다.

예를 들어, 로그 위치가 확인된 상황에서는 다음처럼 쓴다.

```diff
- 오류 발생 시 로그 확인 작업을 수행하세요.
+ 요청이 실패하면 애플리케이션 서버의 /var/log/app/error.log를 확인하세요.
```

## 용어와 문체를 일관되게 쓴다

대화는 기존 문체를 따르고, 문서·리포트 본문은 다체를 기본으로 하되 사용자가 지정한 문체와 대상 프로젝트의 관례를 우선한다.

같은 개념은 같은 용어로 부른다. 비즈니스·기술 용어와 코드 identifier(예: `retention`, `userId`)는 영어 원문을 그대로 쓰고, 제품명·API명은 공식 표기와 대소문자를 따른다. 독자가 모를 약어는 필요한 경우 영어 전체 이름을 함께 쓴다.

목록은 병렬인 항목에 쓰고 문법 형태를 맞춘다. 관계와 이유를 설명할 때는 연결된 문장으로 쓴다. 강조는 핵심 결론과 필요한 주의 사항에 한정한다. 정보 없는 굵은 라벨·콜론·장식용 구분선·이모지를 넣지 않는다.

## 상투적인 AI 문체를 줄인다

- 주장을 직접 쓴다. ‘X가 아니라 Y’ 대비는 실제 차이를 설명할 때만 쓰고, 제기되지 않은 반론에 미리 방어하지 않는다.
- ‘살펴보겠습니다’ 같은 예고, 독자의 반응을 가정하는 말, 깊어 보이기 위한 비유·격언, 상투적 AI 어휘·광고성 수식을 넣지 않는다.
- 항목 수는 의미에 맞춘다. 억지로 세 항목을 맞추지 않고, 문장 시작과 길이는 내용의 흐름에 맞춘다.
- 문장 연결용 대시를 남용하지 않는다. 마침표·쉼표·괄호로 관계를 표현하고, 하이픈·인용부호·영어 제목의 대소문자는 문법과 대상 문체에 맞춘다.
- 독립 문서에서는 상투적인 칭찬·인사·마무리·추가 작업 제안·작성 과정 설명을 넣지 않는다. 끝맺음에 앞 내용을 되풀이하는 한 줄 결론·극적인 단문·교훈을 붙이지 않는다.

인용·고유명사는 정확하게 쓴다. 대시·접속어·한정어처럼 단독으로는 자연스러운 표현은 반복과 문맥을 보고 판단한다.

## 작성한 내용을 확인한다

제목과 개요가 약속한 답을 본문이 제공하는지, 독자가 필요한 정보에 접근해 판단이나 행동을 마칠 수 있는지 확인한다. 실행·사실 확인이 끝나지 않은 내용을 확인된 결과처럼 쓰지 않는다.

렌더링이나 미리보기를 볼 수 있다면 제목 위계·표·코드·그림·링크가 실제 화면에서도 의미에 맞게 표시되는지 확인한다.
