# vibe writing

한국어 기술 문서·리포트를 작성·개선하거나 긴 한국어 기술 설명을 작성할 때 사용한다. 독자의 질문에서 구조를 정하고, 결론·근거·예시를 연결한 뒤 문장을 교정한다. 짧은 사실 답변에는 문서 구조 규칙을 적용하지 않는다. 문서 등록·UI 구현·Git 작업은 대상 프로젝트의 지침을 따른다.

제목·개요·목차에 관한 기준은 해당 요소가 있는 출력에만 적용한다.

## 독자의 질문에서 구조를 정한다

원자료를 문서로 옮기기 전에 다음 세 가지를 정한다. 자료와 요청에서 알 수 있으면 질문하지 않는다.

- 누구에게 필요한 문서인가
- 그 사람이 해결하려는 질문은 무엇인가
- 읽고 나면 무엇을 판단하거나 할 수 있는가

한 문서는 중심 질문에 답한다. 같은 대상을 다뤄도 개념 설명, 사용 절차, 값의 참조, 설계 이유는 읽는 목적이 다르다. 종류가 섞이면 질문별로 구분할 필요가 있는지 검토한다. 페이지 수나 제목 개수만으로 분리를 강제하지 않는다. 앞 단계의 결과가 다음 단계에 필요한 절차, 하나의 사건이나 결정을 기록한 문서는 한 문서에 두는 편이 낫다.

새 문서가 기존 문서와 연결되는 경우 현재 목록과 링크를 먼저 확인한다. 독자의 목적이나 정보의 깊이가 다르다는 부분을 명시하고, 정보 구조를 바꾸는 중요한 판단은 확인한다. 요청받지 않은 사이트 재편이나 관련 없는 문서 수정으로 범위를 넓히지 않는다.

## 제목은 주제, 개요는 답

제목은 내용을 예상할 수 있는 주제형으로 쓴다. 목록과 상세가 있는 문서는 같은 제목을 사용한다. 주장이나 핵심 결론은 개요에 둔다. 제목에는 감탄이나 호기심 유발 문구를 쓰지 않는다.

개요에는 중심 질문의 답과 본문이 설명할 범위를 담는다. 독자가 얻는 결과를 먼저 쓰고, 필요 조건이나 배경은 그 뒤에 둔다. 결론을 아직 확인할 수 없다면 확인한 범위와 부족한 근거를 먼저 밝힌다.

예시:

- 제목: 읽기 좋은 문서를 위한 디자인 시스템
- 불충분한 개요: 이 문서에서는 디자인 시스템을 설명한다.
- 개선한 개요: 흑백 타이포그래피와 파스텔 섹션을 조합한다. 토큰부터 리포트까지 같은 시각 언어로 연결하는 구조를 설명한다.

짧게 쓰려고 조건을 빠뜨리지 않는다. ‘이 문서에서는’ 같은 표현을 일괄 금지하지는 않지만, 그 표현만으로 주제를 반복하고 답이나 범위를 제공하지 않는 개요는 고친다.

## 독자의 목적에 맞게 정보를 배치한다

| 문서의 목적 | 기본 흐름 | 독자가 확인할 결과 |
| --- | --- | --- |
| 처음 사용하기 | 목표 → 준비 → 실습 → 결과 확인 | 예제를 따라 원하는 결과를 만든다 |
| 문제 해결 | 증상 → 원인 → 해결 → 재확인 | 같은 조건에서 문제가 사라졌는지 확인한다 |
| 설계·리서치 | 결론 → 조건 → 비교·근거 → 적용·미확인 | 어떤 조건에서 결론을 적용할지 판단한다 |
| 참조 | 짧은 개요 → 찾을 수 있는 항목 → 의미·형식·예시 | 필요한 값을 빠르게 확인한다 |

흐름은 출발점이지 고정 목차가 아니다. 원자료와 독자의 질문에 필요한 섹션만 둔다. 없는 자료로 선택적 섹션을 채우거나 빈 제목을 남기지 않는다. 필수 정보가 없으면 정확히 어떤 자료가 부족한지 질문한다.

각 섹션은 하나의 주제를 설명한다. 그 섹션을 지웠을 때 독자가 중심 질문에 답하지 못하는지 확인한다. 필요한 정보지만 주된 흐름을 끊는 긴 참조 표나 세부 옵션은 뒤쪽 참조 섹션에 두거나 찾을 수 있는 페이지로 분리한다.

같은 수준의 제목은 같은 종류의 정보를 나타내야 한다. h1은 문서 제목, h2는 섹션, h3는 섹션 안의 소제목이다. 크기를 작게 보이게 하려고 제목 수준을 건너뛰지 않는다. 깊이가 계속 늘면 섹션의 범위가 너무 큰지 확인한다.

## 결론, 근거, 미확인을 구분한다

- 결론은 문서나 섹션의 앞에서 직접 말한다.
- 근거는 확인한 원자료·코드·측정 결과로 연결한다. 조건, 범위, 단위를 함께 쓴다.
- 판단은 근거에서 무엇을 추론했는지 설명한다. 개인의 선호를 객관적 측정으로 표현하지 않는다.
- 미확인은 무엇을 아직 확인하지 못했고 어떤 결론에 영향을 주는지 밝힌다.

내용의 의미, 결정 이유, 수치를 원자료 없이 바꾸지 않는다. 단어를 쉽게 고치는 작업과 사실 판단을 바꾸는 작업을 구분한다. ‘빠르다’, ‘많다’, ‘일부’, ‘적절하다’를 고칠 구체적 근거가 없으면 수치를 만들지 않고 현재 확인된 조건을 쓰거나 질문한다.

예를 들어 팔레트가 근사값이면 ‘Figma의 정확한 브랜드 값’이라고 쓰지 않는다. 측정하지 않은 속도·접근성·성능 개선을 효과로 주장하지 않는다.

## 개념에서 예제로 이어지게 한다

새로운 핵심 개념은 처음 등장할 때 한두 문장으로 풀어 설명한다. 필요한 경우 어디에 쓰이는지도 덧붙인다. 용어를 같은 용어로 되풀이하는 설명을 피한다.

코드·표·이미지를 보여주기 전에 무엇을 설명하거나 비교하는지 설명한다. ‘다음 표를 참고한다’로 끝내지 않고 표가 답하는 질문을 알려준다. 예시 뒤에는 독자가 결과를 어떻게 읽거나 확인하는지 설명한다.

예시:

- 맥락 없는 설명: 다음 코드를 사용한다.
- 맥락을 제공한 설명: `ColorBlock`은 배경색과 안쪽 여백을 만든다. 다음 예시는 연보라색 배경에 요약 제목과 본문을 배치한다.

변수나 속성은 이름뿐 아니라 의미, 허용 형식, 단위, 적용 조건, 필요한 예시를 설명한다. 앞에서 만든 값을 다시 쓰면 어디서 나온 값인지 연결한다. 코드 예제는 대상 프로젝트의 현재 API와 맞아야 한다.

표는 같은 속성을 비교할 때 쓴다. 단순 설명 문장을 표 셀로 잘게 나누지 않는다. 비교 기준과 행·열의 역할을 일관되게 유지한다.

## 문장은 구조를 정한 뒤 교정한다

대화 답변은 기존 대화의 문체를 따른다. 문서·리포트 본문은 다체를 기본으로 하되, 사용자가 지정한 문체와 대상 프로젝트의 관례를 우선한다. 해요체를 전제한 외부 기준을 그대로 적용해 문체를 바꾸지 않는다.

- 의미를 유지하며 수동형과 명사형을 직접적인 동사로 바꾼다.
- ~를 통해, ~에 있어서, ~함으로써가 문장을 늘리면 실제 수단과 행동을 짧게 쓴다.
- 같은 개념은 같은 용어로 부른다. 필요한 약어는 처음에 풀어 설명한다.
- 목록은 서로 병렬인 항목에 쓰고 문법 형태를 통일한다. 관계가 중요한 설명은 연결된 문장으로 쓴다.
- 제목 끝의 마침표·느낌표와 답 없이 호기심만 유발하는 질문형 제목을 피한다. 실제 FAQ의 질문과 즉시 이어지는 답은 예외다.
- 문서가 이해되려면 필요한 주체·조건·단위는 생략하지 않는다.
- 장식용 이모지와 과한 강조를 넣지 않는다. 강조는 실제 결론이나 필요한 주의 사항에 사용한다.

## 구조 검토와 자기 확인

작성 후 출력에 해당하는 다음 항목을 문장 단위 교정보다 먼저 확인한다.

1. 제목과 개요만 읽어도 주제·답·범위를 알 수 있는가
2. 목차와 각 섹션의 첫 문장이 중심 질문에 연결되는가
3. 결론 다음에 조건·근거가 있고, 예시가 설명한 개념을 실제로 보여주는가
4. 주제와 깊이가 다른 내용이 섞이거나 새 개념이 설명 없이 등장하지 않는가
5. 표·코드·그림 앞에 맥락이 있고 독자가 결과를 해석할 수 있는가
6. 출처가 주장을 뒷받침하며 사실·판단·미확인이 구분되는가
7. 같은 수준의 제목과 용어가 일관되고, 빈 섹션·임시 문구가 남지 않았는가
8. 실제 렌더링이나 미리보기를 확인할 수 있다면, 화면에서도 제목 위계·순서·표·본문의 관계가 읽히는가

구조 문제를 먼저 고친 뒤 자연스러운 한국어, 명확한 표현, 맞춤법, 용어를 확인한다. 수정한 문장이 중요한 사실이나 판단을 바꾸지 않았는지 원자료와 대조한다. 실제 개인 정보나 인증 키처럼 구체적으로 발견된 민감 정보는 문서에 옮기지 말고 목적에 필요한 대체 자료를 사용한다.

## 출처와 적용 범위

이 기준은 다음 자료의 필요한 원칙을 한국어 기술 문서·리포트와 긴 기술 설명에 맞게 종합했다. 링크와 경로는 출처이며 다른 스킬이나 도구의 설치 의존성이 아니다.

- Toss · 문서 구조 만들기: 독자의 유형과 목적에 맞는 정보 구조, 문서 간 연결
- Toss · 가치를 먼저 제공하기: 얻는 결과와 결론을 먼저 전달
- Toss · 예측 가능하게 하기: 제목·용어·정보 순서의 일관성
- Toss · 자세히 설명하기: 새로운 개념과 동작 조건의 맥락
- 로컬 doc-evaluator의 reader-first·document-scoping·clear-expression·title-writing 원칙: 구조를 먼저 검토하고 사실 판단을 보존

외부 템플릿의 특정 글자 수·필수 표·해요체·리뷰 승인 절차를 모든 리포트에 강제하지 않는다. 이 문서의 목적은 요청한 자료의 의미를 보존하면서 읽는 구조를 개선하는 것이다.
