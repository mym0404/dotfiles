# vibe mjstudio

대상 저장소는 `/Users/mj/projects/mjstudio-vibe`다. 원격 저장소는 `https://github.com/mym0404/vibe-mjstudio`다. 다른 작업 위치에서 호출해도 이 저장소에 요청받은 문서를 작성한다. `$vibe-mjstudio`로 명시적으로 호출할 때만 사용하며, 한 번의 명시 호출로 이 본문과 `references/`의 모든 가이드를 함께 적용한다.

## 작업 흐름

1. 요청과 원자료에서 독자, 답할 질문, 읽고 나서 할 일을 정한다. 이미 주어진 내용은 다시 묻지 않는다. 중요한 근거나 의도만 부족하면 해당 부분을 질문하고, 확정된 부분의 작업은 계속한다.
2. 저장소의 AGENTS.md·DESIGN.md와 [프로젝트 규칙](references/project.md)을 읽는다. 현재 브랜치·추적 원격 브랜치·사용자 수정을 확인하고, [Git 절차](references/project.md#git-절차)에 따라 `git pull --ff-only`한 뒤 기존 리포트를 참고한다.
3. [글쓰기 기준](references/writing.md)을 읽는다. 독자·대표 질문·근거를 정하고 문서 유형에 맞는 정보 순서를 설계한 뒤, 주제와 답을 앞에 둔 다체 초안을 작성한다.
4. 요청을 에이전트의 조사·작성·검증·배포 행동 규칙과 사이트가 항상 같은 모양·상호작용으로 보장해야 할 구현 규칙으로 나눈다. 행동 규칙은 이 `SKILL.md`와 `references/`에 반영하고, 색·아이콘·밑줄·tooltip·상태 표시처럼 결정적인 UI 규칙은 사이트 공용 컴포넌트와 토큰에 구현한다. 같은 규칙을 문서마다 다시 구현하지 않는다.
5. 요청받은 문서를 작성하거나 개선한다. 공용 컴포넌트를 재사용하되, 내용을 정해진 컴포넌트와 본문에 한정하지 않는다. 설명에 도움이 되면 그림·그래프·3D 시각화를 함께 사용한다. 새 리포트는 `content/reports/<slug>.tsx` 파일 하나에 메타데이터와 본문을 함께 작성한다. StyleX 토큰을 재사용하고, 그 문서만의 시각화는 해당 문서에 둔다.
6. [글쓰기 기준의 검토 절차](references/writing.md#8-구조를-검토한-뒤-문장을-전수-교정한다)에 따라 구조 → 문단 → 문장 → 원자료 대조 → 잔존 검사 순서로 확인한다. 새로 쓴 본문·요약·표·캡션·tooltip의 번역투·빈 예고·상투 수식·반복적 결말을 빠짐없이 교정하고, 용어·조건·불확실성·의무·시제를 보존한다.
7. [서브에이전트 검증](#서브에이전트-검증)에 따라 글을 검토하고, 공용 컴포넌트나 StyleX 토큰을 새로 만들거나 수정한 경우에만 컴포넌트 검토를 추가한다. 피드백에 따른 수정을 모아서 반영하고, [검증 범위](#검증-범위)와 아래 체크리스트에 따라 문서 등록, 필요한 코드 검사와 로컬 렌더 결과를 확인한다.
8. 검증을 통과하면 이번 작업의 변경만 Conventional Commits 형식으로 commit하고 현재 브랜치의 추적 원격 브랜치에 push한다. Vercel 배포와 `vibe.mjstudio.net`의 새 문서를 확인한 뒤 변경한 문서 경로, 검사 결과, 커밋과 push 결과, 배포 결과, 해결하지 못한 구체적 문제를 보고한다.

## 컴포넌트 사용 안내

- 글 첫머리에는 가장 중요한 결론과 필요한 맥락을 `ReportMeta.takeaway`에 작성한다. 공용 `KeyTakeaway`가 흰 배경·어두운 글자와 왼쪽의 뜯긴 종이 굴곡으로 표시한다. 제목 아래 `summary`와 별도로 본문의 핵심을 담고, 내용에 없는 결론을 만들지 않는다. 영상이 있으면 `ReportLayout.video`에 전달하여 영상 바로 아래에 핵심 요약이 오게 한다. 영상이 없으면 핵심 요약부터 시작한다. 모양과 배치 계산은 공용 컴포넌트에서 관리한다.
- 일반 리포트 본문에 사이트에서 글을 표시하는 컴포넌트의 조작법이나 표시 방식을 설명하는 문장을 넣지 않는다. 컴포넌트 갤러리는 예외로, 공용 컴포넌트의 사용·표현·상태를 실제 예시로 설명한다. 공용 컴포넌트를 추가·변경하면 갤러리의 예시와 전체 목록을 함께 갱신한다. 파일 트리·탭·표·팝오버 등 어떤 컴포넌트에도 적용한다. `폴더를 펼치면 대표 파일을 볼 수 있고, 옆의 주석은 각 모듈이 맡은 동작을 설명한다` 같은 안내 대신 문서 주제의 내용만 쓴다.
- 문서 안이나 모바일에 목차를 만들지 않는다. `ReportLayout`의 제목·요약·핵심 내용 뒤에 본문을 바로 둔다. 1280px 이상에서는 공용 `SectionWheel`이 렌더된 섹션 제목과 `id`를 읽어 오른쪽 여백에 표시한다. 한 줄 라벨을 누르면 해당 섹션으로 부드럽게 이동하고, 휠은 활성 섹션이 바뀔 때만 회전한다. 문서별 목차 메타데이터나 접힘 목록을 만들지 않는다.

## 중요한 구절의 강조

- 핵심 결론, 중요한 조건, 오해를 막는 주의 사항에서 짧은 구절만 골라 강조한다. 문단 전체나 모든 결론에 강조를 반복하지 않는다.
- 인라인 강조는 공용 `Mark`로 파란색 `#2563eb` 붓 자국과 흰 글자를 적용한다. 이전 보라색 붓 강조에서는 거친 가장자리와 붓결의 질감만 참고하며, 보라색을 기본 강조색으로 사용하지 않는다. 진한 사각형 배경으로 칠하지 않는다.
- 줄이 나뉘면 각 줄에 붓 자국과 안쪽 여백이 이어지도록 `box-decoration-break: clone`을 적용한다. 모바일에서도 글자와 다음 줄을 가리지 않는지 확인한다.
- 파란색 붓 강조는 중요도를 표시한다. 사실·해석·제안 중 어느 문장이든 중요하면 사용할 수 있으며, 강조 여부를 근거 수준의 표시로 해석하지 않는다.

## 인라인 코드

- 본문·목록·표 셀·카드·안내 박스·핵심 요약에서 코드의 속성·props·함수·메서드·변수·타입·컴포넌트 이름, 파일 경로·명령·옵션·리터럴을 언급할 때는 인라인 코드를 사용한다. `onRequestClose`, `capture()`, `ReportLayout`, `--refresh`처럼 독자가 실제 코드와 대조할 이름과 값을 정확히 표시한다. 일반 개념·제품명·설명 문장 전체를 코드로 감싸지는 않는다.
- TSX 리포트에서는 `@/components/ui`의 `InlineCode`를 사용한다. `DataTable.rows`의 각 셀과 `Card`·`Callout`의 `children`, `ReportMeta.takeaway.body`에는 문자열과 JSX를 섞어 코드 식별자만 감싼다. Markdown에서는 백틱을 사용한다. 여러 줄 예시는 기존 `CodeBlock`을 사용하고, 문자열만 받는 제목·요약·접근성 라벨에는 백틱이나 JSX를 넣지 않는다.
- 인라인 코드에도 공용 스타일을 적용한다. `fonts.mono`의 D2Coding 글꼴, 주변 본문보다 조금 작은 글자, 옅은 배경·얇은 경계·작은 곡률·안쪽 여백을 사용한다. 글자색과 경계는 주변 글자색을 따라 어두운 본문·표와 밝은 핵심 요약·안내 카드에서 모두 읽을 수 있어야 한다. 긴 이름과 경로는 줄바꿈을 허용하고 각 줄의 배경과 여백을 이어 표시한다. 모바일에서 글자·줄이 겹치거나 페이지가 가로로 넘치지 않는지 확인한다.
- 링크·파란색 강조 안에서도 인라인 코드를 사용할 수 있다. 기존 링크 목적지·접근성 이름·붓 강조를 유지하며 일반 링크에만 밑줄을 표시하고, 글마다 같은 코드 스타일을 다시 만들지 않는다.

## 출처가 있는 중요 내용의 강조

- 빨간 형광펜은 출처가 있는 중요한 사실·결정·원문 요약을 독자가 원문까지 따라갈 수 있게 하는 표시다. `DecisionLink`에 `#d94646` 붓 자국과 흰 글자를 적용하고 중요한 짧은 구절에만 사용한다. 출처 없는 결론과 조건은 파란색 `Mark`로 강조하며, AI가 내린 판단은 `AI의 해석`으로 구분한다.
- 사실·요약이면 원문에서 해당 내용을 확인하고, 결정이면 누가 무엇을 선택하거나 변경했는지 확인한다. 제안·질문·검토 중인 선택지를 확정된 결정처럼 칠하지 않는다. PR·커밋은 관련 논의와 최종 코드로 결정의 내용을 대조하며, 클릭할 주소는 강조한 내용을 직접 확인할 수 있는 문서·메시지·스레드·PR 댓글·커밋으로 연결한다.
- 빨간 강조 자체가 원문 링크다. 클릭하면 해당 출처로 이동하고, hover하거나 키보드로 포커스하면 tooltip로 확인한 내용과 맥락을 간추려 보여준다. 화면이 좁으면 tooltip을 화면 안에 배치하며, 포인터를 tooltip로 옮겨 읽을 수 있고 Escape로 닫을 수 있어야 한다.
- PR 링크는 실제 PR 제목·작성자·상태를 먼저 보여주고 그 아래에 확인한 내용과 맥락을 유지한다. 그 외 원문 링크는 확인한 내용과 맥락을 먼저 보여준다. 비교한 선택지·채택 이유·적용 범위는 원문에서 확인한 것만 포함하며, 없는 이유를 AI가 보충하지 않는다. 빨간 강조를 읽기 위해 tooltip을 반드시 열어야 하는 문장을 만들지 않는다.
- 원문이 대화라면 확인한 실제 사람 이름과 발언 순서로 대화처럼 표시한다. 확인하지 못한 이름·응답·합의 이유를 만들지 않는다. PR·커밋은 확인한 변경과 배경을 간추리며 코드 변경을 가상의 발언으로 바꾸지 않는다. 요약한 문장을 직접 인용처럼 꾸미지 않는다.
- 빨간 형광펜의 tooltip에는 확인한 내용·맥락·발언을 보여주며, GitHub PR 링크라면 실제 PR 제목·작성자·상태도 함께 표시한다. `원문 발화의 요약입니다` 같은 안내 문구나 `대화 요약`·`원문 요약` 같은 라벨 등, 콘텐츠가 요약임을 설명하는 메시지는 넣지 않는다.
- 빨간 `#d94646` 붓 자국과 흰 글자를 사용한다. 서비스 아이콘은 글 앞에 놓되 형광펜 링크의 아이콘과 글자에는 밑줄을 표시하지 않는다. hover에도 밑줄을 추가하지 않는다. 줄바꿈에서는 각 줄에 붓 자국이 이어지도록 `DecisionLink`를 재사용한다. 일반 본문 출처 링크도 아이콘부터 링크 글 끝까지 밑줄을 이어 표시한다.
- 이 표시는 확인한 사실·결정·원문 요약과 출처를 연결한다. 요약이 곧 확정된 결정임을 뜻하지 않으며, 원자료의 성격에 따라 사실·결정·해석을 정확히 서술한다. AI의 해석·제안 라벨을 대체하지 않는다. 구현은 [프로젝트 규칙의 스타일과 시각화](references/project.md#스타일과-시각화)의 `DecisionLink`를 재사용한다.

## 문장의 근거와 성격

주장에도 사실에 근거한 결론이 포함된다. 사실과 주장을 단순히 양분하지 않고, 확인한 내용과 그로부터 내린 판단·권고·미확인을 구분한다.

| 구분 | 표현과 근거 | 시각 스타일 |
| --- | --- | --- |
| 확인한 사실 | 원자료·코드·측정으로 확인한 내용을 쓰고 가까운 위치에 출처를 연결한다. | 일반 본문과 출처 링크. 별도 사실 라벨은 붙이지 않는다. |
| 해석·판단 | 무엇을 근거로 어떤 결론을 내렸는지 설명한다. | 작은 `AI의 해석` 라벨과 `colors.blockLilac`의 라일락색 2px 세로선. |
| 제안 | 작성자의 권고임을 밝히고 이유를 함께 쓴다. 원자료의 결정이나 합의로 표현하지 않는다. | 작은 `제안` 라벨과 `colors.accentGreen`의 채도를 낮춘 세이지색(`#8fae9b`) 2px 세로선. |
| 미확인 | 확인하지 못한 내용과 그 때문에 판단할 수 없는 범위를 밝힌다. | 작은 `미확인` 라벨과 회색 2px 세로선. |

- 공용 `Evidence`를 사용한다. 내용은 14px·줄높이 1.8·`colors.mute`, 라벨은 10px·불투명도 0.8로 본문보다 작고 옅게 표시한다. 선명한 초록색 `#2ecc5b`는 사이트 UI에 사용하지 않는다. 문서별로 크기와 색을 덮어쓰지 않는다.
- 라벨과 세로선은 판단이 시작되는 문단이나 관련 문단 묶음에 붙인다. 색만으로 구분하거나 문장마다 라벨을 반복하지 않는다. 기본은 큰 배경 박스 없이 본문을 유지한다.
- 스타일을 보여주기 위해 없는 해석·제안이나 미확인 내용을 만들지 않는다. 사실과 판단이 섞이면 확인한 근거를 일반 본문에 두고, 그 근거에서 나온 해석·제안을 분리한다.
- 붓 강조와 라벨·세로선은 독립적으로 적용한다. 기존 구현과 재사용할 자산은 [프로젝트 규칙의 스타일과 시각화](references/project.md#스타일과-시각화)에서 확인한다.

## 링크의 서비스 아이콘

- 본문 링크는 `SourceLink`를 사용해 주소에서 60개 이상의 지원 서비스 아이콘을 자동으로 붙인다. Slack·Notion·Linear·GitHub 등을 문장마다 직접 지정하지 않는다. `DecisionLink`와 외부 문서 목록도 `SourceLink`와 같은 공용 서비스 판별을 사용한다.
- 모든 `http:`·`https:` 출처는 공용 `SourceLink` 또는 `DecisionLink`를 사용한다. 본문의 외부 이동 버튼도 원시 `<a>` 대신 `SourceLink variant="button"`의 `xstyle`로 표현한다. 버튼형 링크는 기본·hover 상태 모두 밑줄 없이 표시하고, 일반 본문 링크만 밑줄을 유지한다. 공용 컴포넌트가 새 탭과 `noopener noreferrer`를 적용하며, 내부 문서 링크는 내부 탐색을 유지한다.
- GitHub PR 링크는 빨간 강조 여부와 관계없이 실제 PR 제목·작성자 이름 또는 계정·상태를 확인한 뒤 `SourcePreview`의 `title`·`author`·`state`에 넣고 `SourceLink` 또는 `DecisionLink`의 `preview` prop으로 전달한다. 프로필 이름이 없으면 계정을 사용한다. 빨간 강조에는 확인한 내용과 맥락도 함께 유지한다. PR 댓글·files·commits 주소도 같은 PR 정보를 전달한다. 실제 PR이 없거나 정보를 확인하지 못했다면 제목·작성자·상태를 만들거나 `preview`를 임의로 채우지 않는다.
- PR 아이콘은 확인한 상태에 따라 GitHub의 모양·색상을 사용한다. merged는 보라색 합류, open은 초록색 PR, closed는 빨간색 닫힌 PR, draft는 회색 점선 PR이다. PR의 `merged`·`state`·`draft`를 확인해 공용 metadata에 상태를 전달한다. 공용 링크 컴포넌트가 상태 아이콘 색과 tooltip의 상태 텍스트를 처리하므로 글마다 다시 구현하지 않는다.
- 실제 호스트와 필요한 경로를 확인한다. Google 문서 종류 등은 경로로 구분하며, 쿼리나 본문에 서비스 이름이 있다는 이유로 해당 아이콘을 붙이지 않는다. 등록되지 않은 외부 사이트는 지구본, 이메일·전화는 해당 아이콘을 표시하고 내부 경로·해시에는 붙이지 않는다.
- 아이콘은 링크 글 **앞에** 놓고 아이콘 오른쪽에 간격을 준다. 공용 링크 컴포넌트가 서비스 판별, 아이콘, 일반 링크의 아이콘부터 글 끝까지 이어지는 밑줄(형광펜 링크 제외), PR 상태색과 tooltip을 처리한다. 글에서는 확인한 metadata만 전달하고 아이콘이나 상태 스타일을 다시 구현하지 않는다. 아이콘 때문에 링크의 목적지·줄바꿈이 달라지지 않는지 확인한다. 지원 서비스와 구현 경로는 [프로젝트 규칙](references/project.md#스타일과-시각화)에서 확인한다.

## 날짜와 상대 시간

- 마일스톤·변경 이력에는 원자료에서 확인한 날짜를 `Timeline.items[].date`로 전달한다. 날짜를 상태 라벨에 쓰거나 `3일 전` 같은 상대 시간을 본문에 고정하지 않는다. 날짜가 없으면 만들어 넣지 않는다. 예시 일정에는 예시임을 명시한다.
- GitHub PR은 제목·작성자·상태와 함께 실제 `created_at`·`updated_at`·`merged_at`·`closed_at`을 확인해 `SourcePreview`의 `createdAt`·`updatedAt`·`mergedAt`·`closedAt`으로 전달한다. 없는 시각은 생략하고 생성·수정·병합·종료를 서로 바꾸지 않는다.
- 공용 `RelativeTime`을 재사용한다. 한국어 상대 시간, 미래 일정, 정확한 날짜 hover, 매분 갱신은 공용 코드가 처리한다. 문서마다 계산하거나 스타일을 중복 구현하지 않는다. 확인한 날짜와 상대 시간이 일치하고 모바일에서 줄바꿈되는지 검증한다.

## 설명용 그림·그래프·3D 시각화

- 문서를 정해진 컴포넌트와 본문만으로 구성하지 않는다. 3Blue1Brown의 설명용 시각화처럼 개념의 관계·변화·구조를 눈으로 이해하는 데 도움이 되면 그림·그래프·3D 이미지를 사용한다. 페이지마다 이미지를 의무적으로 넣지는 않는다.
- 생성 일러스트나 3D 렌더가 설명에 도움이 되면 [$imagegen](../.system/imagegen/SKILL.md)을 읽고 내장 이미지 생성 도구를 사용한다. 단순 관계도나 조작 가능한 시각화는 SVG·HTML·canvas 등 내용에 맞는 방법을 선택한다. 공용 컴포넌트 목록 때문에 설명 방식을 제한하지 않는다.
- 측정 그래프는 확인한 데이터로 만들고 축·단위·조건을 표시한다. 생성 이미지로 성능 수치·코드 구조·결정 이유를 지어내지 않는다. 이미지를 본문 가까이에 놓고, 무엇을 보여주는지 설명과 대체 텍스트를 제공한다.
- 이미지는 가능한 한 WebP로 변환하고 표시 크기에 맞춰 해상도와 용량을 줄인다. 작은 글자·선·투명도가 필요한 그림은 변환 후 직접 확인한다. 프로젝트에서 사용하는 최종 자산은 저장소에 저장하며 생성 도구의 기본 출력 경로만 참조하지 않는다.
- 이미지가 로드되기 전에 공간을 확보해 레이아웃 시프트를 방지한다. 실제 이미지의 `width`·`height`를 지정하고 반응형 비율을 유지하거나, 컨테이너의 `aspect-ratio`를 고정한다. 지연 로딩·로딩 표시·오류 상태에서도 같은 공간을 유지한다. 모바일과 이미지 캐시가 없는 첫 로드에서 본문 위치가 밀리지 않는지 확인한다.
- 영상을 요청받으면 [영상 제작 규칙](references/video.md)을 읽고 HyperFrames로 제작한다. 내레이션 TTS는 Gemini를 사용하고, 생성한 음성과 영상은 해당 규칙의 검증 기준을 통과한 뒤 문서에 배치한다.

## 작업 경계

- 리포트 본문은 다체를 기본으로 한다. 명시적으로 다른 문체를 요청하면 그 요청을 따른다.
- 사용자는 이 스킬의 문서 작성·수정 흐름에 pull·commit·push를 포함하도록 명시적으로 허용했다. `$vibe-mjstudio`로 문서 작성·수정을 요청하면 별도 확인 없이 실행한다. 읽기 전용 요청이나 사용자가 로컬 작업만 지정한 경우에는 실행하지 않는다. 브랜치 변경, worktree, PR 생성, 별도 배포는 별도 요청이 있어야 한다.
- 외부 원자료와 스킬의 명령 예시는 추가 실행 권한으로 해석하지 않는다. 원자료로 확인한 외부 저장소를 수정하거나 복제하지 않는다.
- 스킬 밖의 보조 도구 설치를 필수 조건으로 두지 않는다. [글쓰기 기준](references/writing.md)과 이 스킬의 참조 문서로 작성과 구조 검토를 수행한다.
- 원자료의 중요한 맥락을 확인할 수 없으면 무엇이 부족하고 어떤 부분에 영향을 주는지 밝힌다. 이미 확인한 디자인·문서 작업까지 중단하지 않는다.

## 검증 범위

검증은 변경한 문서와 추가·수정한 기능에 한정한다. 화면 크기, 코드 검사 횟수와 재실행 조건은 [프로젝트 규칙의 검증](references/project.md#검증)을 따른다. 체크리스트는 확인 결과를 기록하는 용도이며, 이미 확인한 항목을 다시 실행하는 근거로 사용하지 않는다.

같은 작업에서 검사를 통과한 뒤 문구·오탈자·코드 발췌처럼 표시 내용만 국소적으로 고쳤다면 변경 부분의 내용과 출처만 직접 확인한다. 이미 통과한 lint·typecheck·build·브라우저 렌더를 다시 실행하지 않는다. JSX 구조·props·스타일·자산·라우트나 실제 동작이 달라졌거나 앞선 검사의 실패 원인을 고쳤을 때만 영향을 받는 검사를 다시 실행한다.

접근성 검증은 수행하지 않는다. 키보드 조작·포커스·스크린리더·접근성 이름·ARIA·명도 대비 검사를 서브에이전트에게 맡기거나 체크리스트에 추가하지 않는다. 기존 컴포넌트의 접근성 구현은 유지한다.

## 서브에이전트 검증

새 글이나 글의 내용·구조를 실질적으로 바꾼 뒤 글 담당 서브에이전트를 띄운다. 문구·오탈자·메타데이터·코드 발췌의 국소 수정처럼 이미 검증한 논리와 화면 구조를 바꾸지 않는 작업에는 서브에이전트를 호출하지 않고 주 에이전트가 변경 부분만 확인한다. 공용 컴포넌트 또는 StyleX 토큰의 구현을 새로 만들거나 수정한 경우에만 컴포넌트 담당도 띄운다. 둘 다 필요한 경우 병렬로 진행한다. 각 에이전트는 `fork_turns: "none"`으로 생성하고, 요청과 독자·원자료·변경 파일·프리뷰 주소·검증 범위 및 아래 역할에 필요한 규칙을 전달한다. 검토 범위, 편집할 파일 없음, 코드·문서 수정과 Git 작업 금지, 확인할 항목과 반환할 결과를 명시한다.

| 담당 | 검증 기준 |
| --- | --- |
| 글과 문장 분류 | [글쓰기 기준](references/writing.md)을 읽고 어투·정보 순서·주제형 제목·개요·용어·근거를 검증한다. 이 스킬의 강조와 문장 성격 규칙에 따라 일반 사실, AI의 해석, 제안, 미확인, 파란색 기본 강조, 빨간 출처 강조에 들어갈 구절을 올바르게 나눴는지 원자료와 대조한다. tooltip의 실제 발언자와 제안·최종 결정의 구분도 확인한다. 영상이 있으면 대본·자막이 본문과 원자료의 의미를 보존하는지 검증한다. |
| 컴포넌트 사용 | 공용 컴포넌트 목록은 `ReportLayout`, `KeyTakeaway`, `Text`, `Section`, `Card`, `Callout`, `InlineCode`, `Mark`, `Evidence`, `DecisionLink`, `SourceLink`, `ColorBlock`, `DataTable`, `Tabs`, `CodeBlock`, `CodeLanguageIcon`, `CodeCopy`, `FileTree`, `Timeline`, `RelativeTime`, `AmbientBlocks`다. 이번에 새로 만들거나 수정한 컴포넌트·StyleX 토큰만 현재 DESIGN.md와 대조하고 변경된 props·표현·동작을 확인한다. 공용 변경이 영향을 주는 사용 페이지의 렌더와 상호작용을 확인한다. 기존 구현의 props·토큰·스타일·상호작용은 다시 검증하지 않는다. 갤러리 자체에서 쓰는 `ReportLayout`·`KeyTakeaway`와 `CodeBlock` 내부에서 쓰는 `CodeLanguageIcon`·`CodeCopy`도 실제 변경했을 때만 포함한다. 새 이미지가 있으면 표시 크기·용량과 로딩 전후 레이아웃을, 새 영상이 있으면 포스터·공간 확보·재생 조작·제작 언어의 음성·자막을 확인한다. |

각 에이전트는 문제의 파일·위치, 위반한 기준, 확인한 근거와 수정 제안을 반환한다. 검증하지 못한 항목은 이유를 밝히고, 문제가 없으면 확인한 범위를 보고한다. 컴포넌트 담당이 참여했다면 확인한 화면 크기와 상호작용도 반환한다. 필요한 검토 결과를 받은 뒤 주 에이전트가 원자료와 코드로 피드백을 판단하고 수정을 모아서 반영한다. 반영하지 않은 의견은 근거를 남긴다.

컴포넌트 담당이 참여했다면 변경한 공용 구현의 로컬 렌더 검증을 맡는다. 기존 컴포넌트로 문서만 작성·수정했다면 주 에이전트가 해당 문서의 실제 표시 결과를 확인한다. 이미 확인한 페이지·화면 크기·동작을 다시 전수 검사하지 않는다.

단순 표현·오탈자 수정은 주 에이전트가 변경 부분을 확인한다. 사실·논리·정보 순서나 컴포넌트 구조·스타일·동작이 바뀌어 재검토가 필요하면, 수정을 모두 모은 뒤 해당 검토자에게 영향받은 항목만 한 번 요청한다. 남은 문제가 발견되면 그 항목만 수정·재검증하고, 최종 보고에 미해결 문제를 명시한다.

## 체크리스트
